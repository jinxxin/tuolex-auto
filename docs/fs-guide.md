# 功能安全模块使用指南（tuoleX auto · ISO 26262）

**简体中文** ｜ [English](fs-guide.en.md)

- **适用版本**：社区版功能安全域（tuoleX auto，ISO 26262:2018 第二版）
- **内置标准能力**：ASIL 判定表（ISO 26262-3 Table 4，36 格 + 短路规则）、ASIL 分解规则（26262-9）、硬件架构度量目标值（26262-5）——平台内置并可直接查看（HARA 页「ASIL 判定表」、分解向导、FMEDA 目标对照），供评审与自查
- **定位**：功能安全工程**工作产品与证据链管理工具**——平台管理工作产品与追溯，不替代认证评估机构的符合性判定

---

## 1. 模块概览

功能安全域是 tuoleX auto 内置模块（导航「功能安全」分组，7 页），覆盖 ISO 26262:2018 从概念到安全案例的工程闭环：

```
HARA 危害分析与定级（S/E/C → ASIL）
   ↓ 每个带 ASIL 的危害事件 → 安全目标 SG
安全需求链（SG → FSC → TSC → 软硬件安全需求，ASIL 沿链传播，支持 X(Y) 分解）
   ↓
安全分析（FMEDA 硬件度量 / FTA 故障树 / DFA 相关失效 + 分解一致性）
   ↓
Safety Case（GSN 论证树 + 证据回链 + 缺口扫描）
贯穿：确认措施（CR/Audit/FSA + 独立性）、安全计划（生命周期裁剪）、审计包导出
```

**平台共同底座**：服务端哈希链审计（防篡改）、电子签名、评审、在线文档、双语。

**标准范围边界**：覆盖 Part 2/3/4/5/6/8/9 的管理与开发工作产品；**不含** Part 7（生产运行）、Part 12（摩托车）；Part 11（半导体）数据模型预留未展开。相邻标准：SOTIF（21448）与网络安全（21434）以引用字段/FMEA 模板联动，不建模块。

## 2. 快速上手

1. **启用功能安全域**：项目列表 → 新建/编辑项目 → 勾选「功能安全（ISO 26262）」；存量 A-SPICE 项目可随时开启（双域并轨）。
2. 进入「功能安全 → FS 概览」确认项目已选择（右上项目下拉只列 fsEnabled 项目）。
3. 推荐路径：**HARA 分析**（模板/手录危害）→ 确认定级 → **安全需求链**（一键生成 SG+FSC+TSC 骨架）→ **安全分析**（FMEDA/FTA/DFA）→ **Safety Case**（生成论证骨架、挂证据、扫缺口）→ **确认措施/安全计划** → 概览「导出审计包」。
4. 演示数据：ADAS AEB 主线全链路已内置（HARA 4 条确认 → 15 需求节点 → FMEDA 达标/未达标两例 → Safety Case 证据挂接 → 确认措施 → 计划）。

## 3. 术语速览（最小集）

| 术语 | 含义 | 页面 |
|---|---|---|
| HARA | 危害分析与风险评估：危害×场景 → S/E/C → ASIL | HARA 分析 |
| S/E/C | Severity 严重度 / Exposure 暴露度 / Controllability 可控性 | HARA 分析 |
| ASIL | 汽车安全完整性等级 QM/A/B/C/D（D 最高） | 全模块 |
| SG | 安全目标（整车层安全要求，**不可分解**） | 安全需求链 |
| FSC/TSC | 功能安全概念 / 技术安全概念 | 安全需求链 |
| HW_SR/SW_SR | 硬件/软件安全需求（26262 Part 5/6） | 安全需求链 |
| X(Y) | 分解记号：按 Y 原级论证、按 X 级开发（如 B(D)） | 安全需求链 |
| FMEDA | 硬件失效模式与诊断分析 → SPFM/LFM/PMHF 度量 | 安全分析 |
| FTA/DFA | 故障树 / 相关失效分析（独立性论证必查） | 安全分析 |
| GSN | 安全论证图形符号（Goal→Strategy→Solution） | Safety Case |
| CR/Audit/FSA | 确认评审/功能安全审核/功能安全评估（三类确认措施） | 确认措施 |
| I0-I3 | 独立性等级（I0 不同人 → I3 不同部门/组织） | 确认措施 |

## 4. 页面操作详解

### 4.1 HARA 分析（/fs/hara）

**做什么**：录入危害事件、按 S/E/C 三参数定级（引擎实时算 ASIL）、确认定级（评估基线）、导出工作表。

**操作**：
1. **新增危害**：填写危害事件标题、车辆级危害、运行场景；选 S/E 与 C（下拉带等级中文定义）——ASIL 徽标随选择实时更新（判定表 = ISO 26262-3 Table 4）。
2. **从模板引入**：ADAS/BMS/通用模板勾选批量导入（S/E/C 为**参考建议值**，需工程确认）。
3. **条目即工作项**：点击编号/行 → 右侧详情抽屉（全字段 + 三参数定义 + 审计轨迹时间线）。
4. **确认定级**：定级理由必填（HARA 报告证据）；确认后危害进入 SG 生成候选。
5. **人工覆写**：特殊论证（如标准 6.4.3.11 低概率组合论证 QM）→ 开覆写开关 → 手选 ASIL + **覆写原因必填**（审计留痕）。
6. **ASIL 判定表**：右上「ASIL 判定表」只读对照（36 格 + 注 a），评审透明。
7. **导出 HARA 表**：Excel 3 sheet（数据/判定表/参数定义），自动记 EXPORT 审计。

**领域提示**：HARA **不考虑 item 内部安全机制**（那是后置措施）；定级**保守**（有疑取高）；S/E/C 是工程判断，平台给计算辅助与留痕。

### 4.2 安全需求链（/fs/safety-chain）

**做什么**：维护 SG→FSC→TSC→软硬件需求树，ASIL 沿链传播，支持分解；链完整性自动扫描。

**操作**：
1. **从 HARA 生成 SG**：勾选已确认危害 → 生成 SG 草稿（可勾「含 FSC/TSC 骨架」一键三层），危害自动回写 sgId。
2. **树操作**（节点右侧图标）：打开工作项详情 / 新增下级（类型按父级规则限制）/ 编辑 / **ASIL 分解** / 作废 / 删除。
3. **新增/编辑**：子级默认**继承父级 ASIL**；关闭继承手选若**高于父级会告警**（链上不许偷偷提级）；叶子（软硬件/系统安全需求/HSI）建议填**验证方法**（链完整性检查项）。
4. **ASIL 分解向导**：对 FSC/TSC 等（SG 除外）→ 选组合方案（默认双冗余 B(D)+B(D)，另有 C+A、D+QM 等，合法性按 26262-9 表 1 校验）→ 每路选手/硬件类型 + 独立性声明必填 → 生成 X(Y) 子需求，父级记录分解。注意：QM(X) 路径须论证独立性、部分评估机构持保留；硬件度量与确认措施独立性**按分解前原级**。
5. **A-SPICE 承接链接**（见 §5）：需求详情抽屉内按映射推荐层快速建链。
6. **链缺口卡**（右上统计）：点击看明细（SG 无 FSC / FSC 无 TSC / TSC 无软硬件需求 / 叶子无验证方法 / ASIL 提级 / 悬空节点），补全后自动转绿。

### 4.3 安全分析（/fs/analysis，三 Tab）

**FMEDA 度量台**：
1. 新建分析：分析对象（如 AEB 控制器）+ 目标 ASIL（B/C/D 有定量目标；A/QM 无）。
2. 逐行填失效数据：元件/失效模式/**故障分类**（单点残余/潜伏/安全被探测/无影响 QM）/ λ（FIT）/DC%/安全相关开关/安全机制。
3. 底部**实时度量**：SPFM/LFM/PMHF + 目标对照（D 级：PMHF<10FIT、SPFM≥99%、LFM≥90%）+ 达标判定。口径：分子=单点+潜伏；分母=全部安全相关行（含安全类）；**QM 行（关掉安全相关开关）完全排除**——与 ISO 26262-5 C.2 / TI 算例一致。
4. 提示：平台用简化线性模型（Annex C 近似），复杂架构建议完整概率模型人工复核（UI 已标注）。
5. 快捷：编辑时按分析对象一键插入**常见失效模板**行（MCU/电源/传感器/看门狗）。

**FTA 故障树**：顶事件 + ASIL；递归编辑（AND/OR 门、基本事件可带 λ 可选）；实时文本预览。AND=全发生才触发，OR=任一触发。

**DFA 相关失效**：元素对矩阵（A/B + 级联/共同原因/交互 + 耦合细节 + 防护）；**页顶一致性校验**：项目中每个 ASIL 分解声明（如 TSC-001）必须被至少一条 DFA 行文本引用，否则黄条告警——补引用即转绿（评估机构对分解独立性论证的必查项）。

### 4.4 Safety Case（/fs/safety-case）

**做什么**：以 GSN 论证树组织「系统功能安全可接受」的论证与证据。

**操作**：
1. 新建案例 → 默认一个顶层 Goal（主张）。
2. 节点行：类型（Goal 主张 / Strategy 策略 / Solution 证据 / Context / Assumption / Justification）+ 文本 + 操作：
   - Goal 可标**未展开 ◇**（草稿占位，缺口扫描会揪出）
   - Solution 点「挂接证据」→ 选证据类型（10 类平台工件：FS 需求/HARA 危害/FMEDA/FTA/DFA/A-SPICE 需求/测试用例/FMEA/验证文档/工作产品）→ 选对象 → 证据可点击回源
   - Goal 可**签核**（人/时间留痕）
3. **一键论证骨架**（生成模板：危害受控 → 策略分论据 → Solution 占位），再逐个补证据。
4. **扫描缺口**：未展开主张/策略无承接/证据未挂接 → Modal 明细；列表缺口数与扫描一致（实时）。
5. 状态流：草稿 → 评审中 → 已批准（终态）。

### 4.5 确认措施（/fs/confirm）

三类确认措施：**确认评审 CR**（关键工作产品，如 FSC/TSC）、**功能安全审核 Audit**（过程）、**功能安全评估 FSA**（item 整体，最高层）。每项含：
- 相关 ASIL + **独立性 I0-I3**（新建时按 ASIL 给默认建议：D→I3、B/C→I2、A/QM→I1，可调整；标准表以项目裁剪与评估机构要求为准）
- 状态流：计划 → 进行中 → 关闭（审计留痕）
- FSA 结论三态：接受 / 有条件接受 / 拒绝（记录在评估结论）
- 建议：HARA/需求链/Safety Case 等关键节点安排 CR；FSA 在发布前完成（C/D 级通常强制）。

### 4.6 安全计划（/fs/plan）

生命周期任务清单（概念/系统/硬件/软件/集成与验证五阶段预设 + 自由阶段）：
- 任务/交付物/ASIL/负责人/期限；状态：计划 → 进行中 → 已完成。
- **NA 裁剪**：某阶段不适用（如无硬件开发）→ 标 NA **必须填裁剪理由**（评估常查「为什么没做」）。

### 4.7 FS 概览（/fs/overview）

域驾驶舱：四阶段状态聚合（HARA 确认率与 ASIL 分布 / 需求链与缺口 / FMEDA 达标率与分解覆盖 / Case 证据与确认措施与计划进度）+ 待办缺口速览（可点击跳转对应页）+ 模块入口 + **导出审计包**（10 sheet xlsx：HARA/需求链/FMEDA+明细/FTA/DFA/Safety Case 节点/确认措施/安全计划/审计轨迹，时间倒序）。

## 5. 与 A-SPICE 的联动（映射规则）

**为什么需要**：双域项目（A-SPICE 过程 + 功能安全）中，26262 安全需求需落到 A-SPICE 的工程需求条目上实现与验证——评估时「安全需求是否被工程条目承接、双向可追溯」是必查证据。

**层级承接规则**（开发与分析结论，实现于 `core/fs/aspiceMap.ts`，UI 按此推荐）：

| FS 层（安全需求） | 承接 A-SPICE req_items 层 | A-SPICE 过程语境 | 依据 |
|---|---|---|---|
| SG 安全目标 | 不建议直链（可链测试/文档） | SYS.1 上游 | SG 是整车危害层，req_items 无对应层 |
| FSC 功能安全概念 | sys_req（系统需求） | SYS.1/SYS.2 | FSR 落到系统需求中 safety-related 部分 |
| TSC 技术安全概念 | sys_req（可切 sys_arch） | SYS.2/SYS.3 | TSR 技术需求/架构措施 |
| SYSTEM_SR 系统安全需求 | sys_req | SYS.2 | 同层承接 |
| HW_SR 硬件安全需求 | hw_req | HWE.1（4.0）/V 层 hw_req | 26262-5 ↔ HWE.1 |
| **SW_SR 软件安全需求** | **sw_req** | **SWE.1** | 26262 Part 6 ↔ SWE.1 safety-related 软件需求（最典型） |
| HSI 软硬件接口 | sys_arch / sw_req | SYS.3/SWE.1 | 接口规格需求 |

**操作方法**：
1. FS 需求详情抽屉 → 「A-SPICE 承接链接」区 → 显示当前类型推荐承接层（Tag 带过程语境）→ 目标层（默认推荐层，可切全部）→ 候选条目下拉（可搜索）→ 「建立链接」。
2. 链接以 trace_links 记录（关系「细化」），**双向**：A-SPICE 需求条目侧（工作项/追溯面板）同样可见并可反向建立 FS 链接（含 FS 需求/危害/分析各实体）。
3. 断链：已链接列表逐条断开（审计留痕）。
4. 实践建议：SG 保持概念层（不落 req_items）；SW_SR 与 SWE.1 软件需求条目建立一对多细化；测试用例回链由安全需求侧挂 tc 完成（验证覆盖证据进 Safety Case）。

## 6. AI 智能搭建（内置模板库）

以**内置模板库**提供（= 云端无 AI key 时的降级内容；本地同源，保证行为一致）：
- HARA 包式生成（ADAS AEB/ACC、BMS、通用电子四套，每套含多条危害+S/E/C 建议）
- 已确认危害 → SG+FSC+TSC 三层骨架（批量）
- FMEDA 常见失效行（按元件匹配）
- Safety Case 论证骨架（Goal→Strategy→Solution）

**铁律**：生成物全部为**草稿态**，S/E/C、ASIL、度量均需工程确认——AI/模板不直接产生已确认的安全数据。

## 7. 审计与合规

- **哈希链审计**：所有 fs 实体写操作自动落服务端审计（创建/更新/删除/确认/作废/链接/导出），防篡改；详情抽屉可查条目级轨迹；概览「导出审计包」含审计 sheet。
- **电子签名**：关键工作产品可经在线文档/签名中心签核（平台底座，FS 报告导出后走签名流程）。
- **评估视角**：交证据包 = 概览 → 导出审计包（工作产品全量 + 审计轨迹）→ 配合 Safety Case 证据回链与确认措施关闭记录。
- 平台**不判定符合性**：ASIL/度量结论是工程判断；引擎给计算与目标对照，边界案例留人工覆写/理由记录。

## 9. FAQ / 常见误区

| 问题 | 说明 |
|---|---|
| 平台能「认证」ISO 26262 吗？ | 不能。平台管证据链，评估机构（SGS/TÜV/中汽研等）做判定。 |
| HARA 时能不能把安全机制算进去降 ASIL？ | 不能。HARA 评估的是故障行为本身；安全机制是后续安全概念的措施。 |
| 定级不确定怎么办？ | 保守取高（标准原则）；边界案例（如 S3+E1+C3）按注 a 走人工覆写留痕。 |
| QM 是不是「不用管」？ | 不是。QM = 不再续做 26262 活动，质量体系要求仍适用。 |
| 分解是不是降级偷懒？ | 不是。分解要求冗余+独立性（DFA 论证）；度量与确认措施仍按分解前原级。 |
| FMEDA 度量是精确值吗？ | 简化模型（线性近似）；复杂架构（多故障路径/维修率）需完整概率模型复核（UI 标注）。 |
| 我的项目没有 A-SPICE 需求条目？ | FS 专项项目可不建链；建链价值在双域项目（§5）。 |
| Safety Case 缺口很多？ | 正常迭代态：◇ 未展开/未挂证据/策略无承接都会列出，补完转绿。 |

## 10. 边界与责任声明

- 内置标准知识为**自写摘要/公开事实**（非 ISO 原文），术语以英文原文为准（中译仅供理解）。
- S/E/C 定级、ASIL 判定、度量结论属**工程判断**；平台记录判断过程与依据，供评估审查。
- 演示数据为公开案例归纳，标注「示例，需工程确认」，不得直接用于真实项目结论。
- 若需进一步定制（Part 11 半导体模板、SOTIF 场景库、评估机构报告格式），联系 jinxxin@live.com。
