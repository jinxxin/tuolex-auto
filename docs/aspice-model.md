## 1. 建模范围

本项目把 A-SPICE 的**过程参考模型**建成一棵可挂证据的树：

```
过程组 → 过程 → 工作产品（WP） → 证据（文档/评审/签名/变更）
```

内置过程组（示例）：

| 组 | 过程（示例） |
|---|---|
| SYS | SYS.1 需求挖掘、SYS.2 系统需求分析、SYS.3 系统架构设计、SYS.4 系统集成与集成测试、SYS.5 系统合格性测试 |
| SWE | SWE.1 软件需求分析、SWE.2 软件架构设计、SWE.3 软件详细设计与单元构建、SWE.4 软件单元验证、SWE.5 软件集成与集成测试、SWE.6 软件合格性测试 |
| SUP | SUP.1 质量保证、SUP.2 验证、SUP.4 联合评审、SUP.5 变更请求管理、SUP.7 文档管理、SUP.8 配置管理、SUP.9 问题解决管理 |
| MAN | MAN.3 项目管理、MAN.5 风险管理、MAN.6 测量 |
| ACQ/SPL | 采购与供应（按需启用） |

> 过程与工作产品的**名称**是行业通用术语；本项目不附带任何标准条款正文。

## 2. 能力等级怎么落

- 每个过程在项目内有 `processStatus`：未开始 / 进行中 / 已达成；
- 达成判定不靠勾选，而靠**证据是否闭合**：工作产品存在 + 评审通过 + （需要时）签名有效 + 变更可追溯；
- 断链检测会列出：无来源的需求、无验证的需求、无评审的交付物、签名失效的评审。

这套判定是**工程化的近似**，用于内部自查与审计准备，不等同于正式评估（Assessment）结论。

## 3. 与评估的差别（务必知晓）

| 正式评估 | 本工具 |
|---|---|
| 由认证评估师按 PAM 执行 | 由团队自查 |
| 抽样访谈 + 证据核验 + 评级 | 规则化断链检测 + 证据索引 |
| 出具能力等级结论 | **不出结论**，只给缺口清单 |

## 4. 数据模型（简）

- `processes`：过程目录（code/name/group）
- `work_products`：工作产品实例（挂项目、过程、状态、文档）
- `requirements` / `test_cases` / `trace_links`：需求、测试与追溯
- `vdocs` / `signatures` / `audit_logs`：文档、签名、哈希链审计

## 5. 扩展

新增过程：在 `server/src/data/processes.ts` 增加条目即可（不改表结构）。
新增工作产品模板：`server/src/data/wpTemplates.ts`。
